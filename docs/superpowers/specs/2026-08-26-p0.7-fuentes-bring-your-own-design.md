# P0.7 — Fuentes (bring-your-own) · Diseño

**Objetivo:** convertir la fuente de canales de un valor sembrado/oculto (URL de IPTV-org hardcodeada + `IPTV_ORG_URL`) en una **funcionalidad de primera clase, gestionada por el usuario**: en el primer arranque el build público no trae ninguna lista cargada, sino un onboarding que deja **pegar una URL M3U o soltar un `.m3u`** y ofrece **fuentes sugeridas de un toque** (IPTV-org global + sub-listas por país/categoría). Así el producto público es limpio (no viene preconfigurado apuntando a un catálogo de terceros), la incorporación de listas es trivial, y el build local del autor conserva todo su catálogo tal cual.

**Por qué (postura ética/legal, resumen):** distribuir una herramienta **precargada** con acceso a un catálogo de streams de terceros de procedencia mixta es el patrón que la ley europea (caso *Filmspeler*, C-527/15) trata como facilitación de infracción. Enviar el producto **vacío + añadir-tu-fuente fácil**, con las listas comunitarias como **sugerencias que el usuario elige activamente**, mueve el producto del patrón "aparato preconfigurado" hacia "reproductor genérico" (categoría VLC/mpv), sin renunciar a la facilidad. No es asesoría legal; P1 incluye una consulta breve con abogado como puerta previa a hacer el repo público.

**Arquitectura:** una capa de **gestión de fuentes** sobre el `Syncer`/`ProviderPort` existentes. El modelo pasa de un único provider sembrado a **N fuentes gestionadas por el usuario** (añadir/quitar/re-sincronizar), sincronizadas y **fusionadas** en el catálogo (los IDs de canal ya llevan namespace por provider, así que no colisionan). El cliente gana un **estado de onboarding**, una **vista de Fuentes**, y añadir por **URL o fichero**. El build público deja de sembrar IPTV-org en instalación limpia; la DB existente del autor no se toca.

**Tech Stack:** Go 1.25 + chi v5 + modernc/sqlite (capa de fuentes + endpoints) · Svelte 5 + TS (onboarding + vista de fuentes) · Vitest + testing-library. Ninguna dependencia nueva.

**Spec relacionada:** hereda todo P0/P0.5/P0.6. La distribución (licencia, disclaimer, releases, notarización, flip público, la consulta legal) es **P1**, no aquí. El caso de estudio de ingeniería en korven.dev es **P4**.

## Decisiones cerradas (con el usuario, 2026-08-26)

1. **Primer arranque del build PÚBLICO: sugeridas de un toque.** Sin fuente cargada; onboarding con campo "pega una URL M3U o suelta un `.m3u`" + una lista de **fuentes sugeridas** (IPTV-org global + sub-listas país/categoría) que el usuario **pulsa para añadir**. El producto NO viene pre-apuntado; el toque del usuario es lo que descarga.
2. **El build local del autor conserva su catálogo completo** — automático: su DB ya tiene IPTV-org sincronizado; solo se retira el *seed en instalación limpia*, no se borra nada existente.
3. **Múltiples fuentes, fusionadas** (no una sola intercambiable): añadir/quitar/re-sincronizar varias; los canales de todas las fuentes activas se fusionan.
4. **Las "fuentes sugeridas" viajan como punteros** (etiqueta + URL M3U) en el binario, **nunca como datos de canales**. Nada cuestionable se embebe; el fetch lo dispara el usuario.

## Modelo de datos y backend

**Fuentes gestionadas por el usuario.** Hoy hay una tabla `providers` sembrada con un único `opensource` (IPTV-org). Cambia a:
- `sources` (o se reutiliza `providers` ampliada): `{ id, etiqueta, url_o_ruta, tipo: 'url'|'fichero', anadida_en, ultimo_sync, estado }`. Varias filas activas.
- El **seed de IPTV-org en `seedProviders` se retira para instalación limpia** (build público): una DB nueva arranca SIN fuentes. La DB existente del autor conserva sus filas (el seed solo insertaba si no existía; no se borra nada). *Ruling:* el dev que quiera reconstruir su DB llena añade IPTV-org de un toque como cualquier usuario, o vía `IPTV_ORG_URL` (que se conserva como atajo de conveniencia/opt-in, documentado, no como default visible).
- El `Syncer` **itera las fuentes activas** y sincroniza cada una (mismo backoff/cap/streaming por fuente); los canales se fusionan. Quitar una fuente elimina sus canales (por namespace de provider). *Consideración:* la salud/latencia y `web_ok` siguen por stream como en P0.5; sin cambios de contrato.

**Endpoints nuevos (solo cliente web, snake_case):**
- `GET /sources` → lista de fuentes con `{id,etiqueta,url,tipo,ultimo_sync,estado,canales}`.
- `POST /sources` → añade una fuente por URL (`{url, etiqueta?}`) o por fichero (multipart `.m3u`, con `io.LimitReader` como el cap M3U existente); dispara sync; responde la fuente creada.
- `DELETE /sources/{id}` → quita la fuente y sus canales.
- `POST /sources/{id}/sync` → re-sincroniza esa fuente.
- `GET /sources/sugeridas` → la lista curada de **punteros** sugeridos (etiqueta + URL) que viaja en el binario (constante Go), p.ej. IPTV-org global + `countries/mx.m3u` + `categories/news.m3u`… El cliente la pinta como botones de un toque que hacen `POST /sources` con esa URL. **No** contiene datos de canales.
- **Validación:** la URL debe ser http/https y **pasa por el mismo fetch del gateway** (no el navegador) con el cap de tamaño y timeout existentes; un M3U vacío/portal-cautivo se detecta como ya hace el `Syncer` (no vaciar el catálogo por un cuerpo truncado). Errores con `%w`/`slog`.

## Cliente (Svelte)

- **Onboarding / estado vacío** (`Onboarding.svelte` o el estado vacío del catálogo cuando no hay fuentes): título "Añade una fuente de canales", un campo prominente **pegar URL M3U** + **soltar/elegir `.m3u`**, y debajo **Sugeridas** (de `/sources/sugeridas`) como botones de un toque. Al añadir → sincroniza → aparece el catálogo. Copy honesto y calmado (voz Korven).
- **Vista de Fuentes** (`Fuentes.svelte`, accesible desde la cabecera/acciones): lista de fuentes añadidas con `ultimo_sync`, re-sincronizar, quitar, y el mismo "añadir" (URL/fichero/sugeridas). 
- **Añadir por fichero:** `<input type="file" accept=".m3u,.m3u8">` → multipart a `POST /sources`. Nada sale del navegador salvo al gateway local.
- **Estado de sincronización** reutiliza la barra indeterminada de P0.6 (por fuente si aplica).
- **i18n es+en** para todo el copy nuevo. **Accesibilidad**: el onboarding y la vista de fuentes cumplen el estándar de P0.6 (nombres accesibles, foco, aria-live donde toque vía la región persistente de App).
- **Sin datos de canales embebidos**: las sugeridas son etiquetas+URL.

## Riesgos

- **Retirar el seed sin vaciar la DB del autor:** el seed solo insertaba si no existía; una DB con datos no se toca. Verificar en el plan que instalar-limpio da 0 fuentes y que la DB de dev conserva las suyas.
- **Fusión multi-fuente / IDs:** los IDs de canal ya llevan namespace por provider; verificar que quitar una fuente no huérfana canales de otra ni rompe favoritos/historial (que referencian canalId).
- **Subida de fichero:** cap de tamaño (`io.LimitReader`) + parseo en streaming como el M3U remoto; un `.m3u` malformado no debe tumbar el gateway.
- **Postura legal:** la decisión de "sugeridas de un toque" es defendible pero la consulta con abogado de P1 puede pedir afinar cuánto se sugiere in-app vs. solo docs; el diseño lo permite (las sugeridas son datos curados fáciles de recortar).
